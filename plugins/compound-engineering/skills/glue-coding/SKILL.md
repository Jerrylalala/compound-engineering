# 胶水编程 (Glue Coding)

本技能提供**完整的项目架构规划**工作流，用于新项目启动或系统设计阶段。

> **注意**：胶水编程的基本原则（写代码前先搜 GitHub）已内置于全局 CLAUDE.md，所有任务自动生效。本技能用于需要**完整架构规划**的场景。

## 核心理念

> **几乎完全复用成熟开源组件，通过最小量的"胶水代码"将它们组合成完整系统**

### 胶水编程铁律

1. **凡是能不写的就不写** - 已有成熟实现的功能，不重新造轮子
2. **不修改原仓库代码** - 开源库作为黑盒使用，保持不可变
3. **自定义代码只承担连接** - 组合、调用、封装、适配

## 何时使用本技能

**积极主动调用** - 本技能应在几乎所有编码任务中被考虑：

**适用场景（默认触发）：**
- 任何新功能开发
- 网页 / Web 应用 / 前端组件
- App（iOS/Android/跨平台）
- 桌面应用（Electron/Tauri）
- CLI 工具 / 脚本
- API / 后端服务
- 数据处理 / ETL 管道
- AI/ML 应用
- 内部工具 / 自动化

**核心原则**：在写任何代码之前，先问「GitHub 上有没有人已经做过这个？」

**仅在以下情况跳过：**
- 纯 Bug 修复（不涉及新功能）
- 单行代码改动
- 项目已明确指定技术栈且不允许引入新依赖

## 工作流程

### Phase 1: 需求拆解

将用户需求拆解为可复用的子模块。

**拆解维度：**

| 维度 | 问题示例 |
|------|---------|
| 核心功能 | 系统必须完成什么？ |
| 数据流 | 数据从哪来、到哪去、如何转换？ |
| 用户交互 | 前端/CLI/API？交互方式？ |
| 存储 | 数据库类型？文件系统？ |
| 第三方集成 | 需要对接哪些外部服务？ |

**输出格式：**

```markdown
## 需求拆解

### 核心模块
1. [模块名] - [职责描述]
2. [模块名] - [职责描述]

### 数据流
[输入] → [处理] → [输出]

### 技术约束
- 语言/框架偏好：
- 部署环境：
- 性能要求：
```

### Phase 2: 搜索开源库

针对每个子模块，搜索 GitHub 上的成熟开源库。

**搜索策略：**

1. 使用 WebSearch 搜索 GitHub
   ```
   site:github.com [功能关键词] [语言] stars:>1000
   ```

2. 使用 gh CLI 获取仓库详情
   ```bash
   gh search repos "[关键词]" --limit 10 --sort stars
   gh repo view [owner/repo] --json stargazersCount,updatedAt,license
   ```

**筛选标准：**

| 指标 | 推荐阈值 | 说明 |
|------|---------|------|
| ⭐ Stars | > 500（优先 > 1000） | 社区验证度，从高到低排序 |
| 🕐 最近更新 | < 12个月 | 仍在维护 |
| 📜 许可证 | 大多数可用 | 仅排除明确禁止商用的（如 AGPL 强制开源） |
| 📚 文档 | 有基本说明 | 能跑起来即可 |

**许可证说明**：95% 的开源许可证（MIT/Apache/BSD/ISC/LGPL/MPL 等）在实际使用中无障碍。仅需注意：
- ❌ AGPL - 要求衍生作品也开源
- ❌ 明确写 "Non-Commercial" 的
- ✅ 其他大多数许可证可放心使用

**输出格式：**

```markdown
## 开源库推荐

### [模块名]: [功能]

| 库名 | Stars | 更新 | 许可证 | 推荐理由 |
|------|-------|------|--------|---------|
| [repo1](url) | 5.2k | 2周前 | MIT | ... |
| [repo2](url) | 3.8k | 1月前 | Apache | ... |

**推荐选择**: [repo1]
**理由**: ...
```

### Phase 3: 架构设计

设计胶水层架构，明确各组件如何连接。

**目录结构模板：**

```
project/
├── src/
│   ├── glue/           # 胶水代码（你写的部分）
│   │   ├── adapters/   # 适配器（统一接口）
│   │   ├── pipelines/  # 数据流管道
│   │   └── config/     # 配置管理
│   └── main.ts         # 入口文件
├── third_party/        # 第三方库（如需本地化）
├── package.json        # 依赖声明
└── README.md
```

**胶水代码职责：**

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  开源库 A   │────▶│  胶水适配器  │────▶│  开源库 B   │
└─────────────┘     └─────────────┘     └─────────────┘
                          │
                    统一数据格式
                    错误处理
                    日志/监控
```

### Phase 4: 输出交付物

生成完整的架构方案文档。

**交付物清单：**

```markdown
# [项目名] 胶水架构方案

## 1. 需求概述
[1-2 段描述]

## 2. 模块拆解
[Phase 1 输出]

## 3. 技术选型
[Phase 2 输出，含推荐库清单]

## 4. 架构设计
[目录结构 + 数据流图]

## 5. 依赖清单
| 依赖 | 版本 | 用途 |
|------|------|------|

## 6. 胶水代码范围
- [ ] 适配器：[列表]
- [ ] 配置：[列表]
- [ ] 入口逻辑：[列表]

## 7. 下一步
→ 安装依赖并搭建项目骨架
→ 实现胶水层代码
→ 集成测试
```

**输出位置**: `docs/architecture/YYYY-MM-DD-<project>-glue-plan.md`

## 搜索技巧

### 按场景搜索

| 场景 | 搜索关键词示例 |
|------|---------------|
| Web 后端 | `nodejs api framework stars:>5000` |
| 数据处理 | `python data pipeline etl stars:>2000` |
| CLI 工具 | `golang cli framework stars:>3000` |
| 前端组件 | `react component library stars:>10000` |
| AI/ML | `python llm inference framework stars:>1000` |

### 评估仓库质量

除了 Stars，还要检查：

1. **Issue 响应速度** - 维护者是否活跃
2. **贡献者数量** - 是否单点依赖
3. **Breaking Changes 频率** - API 稳定性
4. **依赖数量** - 是否过度依赖

## 与现有工作流的关系

### 双层设计

```
┌─────────────────────────────────────────────────────────────┐
│ 层级 1：全局思维（自动生效）                                  │
│ - 内置于 CLAUDE.md                                          │
│ - 任何编码任务都会自动考虑"有没有现成库"                      │
│ - 不中断原有工作流，融入思考过程                              │
└─────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────┐
│ 层级 2：完整规划（手动调用 /glue-coding）                  │
│ - 用于新项目启动、完整架构设计                               │
│ - 输出完整的技术选型文档                                     │
│ - 适合需要系统性规划的场景                                   │
└─────────────────────────────────────────────────────────────┘
```

### 工作流融合（非中断）

```
用户需求
    ↓
/brainstorming（可选）
    ↓ ←── 思考时自动融入胶水思维：有现成库吗？
/workflows:plan
    ↓ ←── 规划时列出可复用的开源库
实现代码
    ↓ ←── 优先调用现成库，只写胶水层
/workflows:review
```

**关键**：胶水编程思维已融入每个阶段，不需要单独"切换"或"中断"。

### 何时手动调用 /glue-coding

| 场景 | 是否调用 |
|------|---------|
| 新项目从零开始 | ✅ 调用，做完整架构规划 |
| 添加一个新功能 | ❌ 不需要，全局思维自动生效 |
| 选择技术栈 | ✅ 调用，系统性对比 |
| 修 Bug | ❌ 不需要 |
| 重构现有系统 | 视情况，大重构可调用 |

## 反模式警告

| ❌ 反模式 | ✅ 正确做法 |
|----------|-----------|
| 修改开源库源码 | Fork 后通过继承/装饰器扩展 |
| 选择最新最酷的库 | 选择最稳定、文档最全的库 |
| 一次性引入大量依赖 | 逐步引入，验证后再添加下一个 |
| 忽视许可证 | 检查许可证兼容性 |
| 胶水代码写业务逻辑 | 胶水只负责连接，业务逻辑用现成库 |
