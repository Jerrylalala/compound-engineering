# 系统化调试

> **核心理念**：随机修复浪费时间，还会制造新 bug。快速补丁只是掩盖问题。

## 铁律

```
没有根因分析，就没有修复
```

如果没有完成第一阶段，**不能**提出修复方案。

**违反规则的字面，就是违反规则的精神。**

---

## 何时使用

**任何技术问题都适用：**
- 测试失败
- 生产环境 bug
- 意外行为
- 性能问题
- 构建失败
- 集成问题

**尤其在以下情况必须使用：**
- 时间紧迫（紧急情况让猜测变得诱人）
- 「一个小修复」看起来很明显
- 已经尝试过多次修复
- 之前的修复没起作用
- 不完全理解问题

**不要跳过：**
- 问题看起来简单（简单问题也有根因）
- 时间紧张（系统化比瞎折腾更快）
- 老板要求立刻修好（系统化方法更快解决问题）

---

## 四个阶段

**必须**按顺序完成每个阶段。

### 第一阶段：根因调查

**在尝试任何修复之前：**

#### 1. 仔细阅读错误信息

- 不要跳过错误或警告
- 错误信息通常包含确切的解决方案
- 完整阅读堆栈跟踪
- 记录行号、文件路径、错误代码

#### 2. 稳定复现

- 能可靠地触发吗？
- 确切的步骤是什么？
- 每次都发生吗？
- 如果不能复现 → 收集更多数据，不要猜测

#### 3. 检查最近的变更

- 什么变化可能导致这个问题？
- Git diff，最近的提交
- 新依赖，配置变更
- 环境差异

#### 4. 在多组件系统中收集证据

**当系统有多个组件时（CI → 构建 → 签名，API → 服务 → 数据库）：**

```
对于每个组件边界：
  - 记录进入组件的数据
  - 记录离开组件的数据
  - 验证环境/配置传递
  - 检查每层的状态

运行一次收集证据，显示在哪里断掉
然后分析证据识别失败的组件
然后调查那个特定组件
```

#### 5. 追踪数据流

**当错误深藏在调用栈中时：**

详见 [根因追踪](./references/root-cause-tracing.md)。

**快速版本：**
- 错误值从哪里来？
- 谁用错误值调用了这里？
- 继续向上追踪直到找到源头
- 在源头修复，而非在症状处

---

### 第二阶段：模式分析

**修复前先找到模式：**

#### 1. 找到工作示例

- 在同一代码库中找到类似的工作代码
- 什么类似的东西是正常工作的？

#### 2. 对比参考

- 如果在实现某个模式，**完整阅读**参考实现
- 不要略读——阅读每一行
- 在应用之前完全理解模式

#### 3. 识别差异

- 工作的和坏的有什么不同？
- 列出每一个差异，无论多小
- 不要假设「这个不重要」

#### 4. 理解依赖

- 这需要什么其他组件？
- 什么设置、配置、环境？
- 它有什么假设？

---

### 第三阶段：假设与测试

**科学方法：**

#### 1. 形成单一假设

- 清晰陈述：「我认为 X 是根因，因为 Y」
- 写下来
- 具体，不要模糊

#### 2. 最小化测试

- 做**最小的可能变更**来测试假设
- 一次只改一个变量
- 不要同时修复多个问题

#### 3. 继续之前先验证

- 成功了？→ 进入第四阶段
- 失败了？→ 形成**新的**假设
- **不要**在上面叠加更多修复

#### 4. 不确定时

- 说「我不理解 X」
- 不要假装知道
- 寻求帮助
- 继续研究

---

### 第四阶段：实施

**修复根因，而非症状：**

#### 1. 创建失败测试用例

- 最简单的复现
- 如果可能，写自动化测试
- 如果没有测试框架，写一次性测试脚本
- 修复前**必须**有这个

#### 2. 实施单一修复

- 解决已识别的根因
- 一次**一个**变更
- 没有「顺便」的改进
- 没有捆绑的重构

#### 3. 验证修复

- 测试现在通过了？
- 没有破坏其他测试？
- 问题真的解决了？

#### 4. 如果修复不起作用

- **停下来**
- 数一下：已经尝试了多少次修复？
- 如果 < 3：返回第一阶段，用新信息重新分析
- **如果 ≥ 3：停下来质疑架构（见下文）**
- 在没有架构讨论的情况下**不要**尝试第 4 次修复

#### 5. 如果 3+ 次修复失败：质疑架构

**表明架构问题的模式：**
- 每次修复都在不同地方暴露新的共享状态/耦合/问题
- 修复需要「大规模重构」才能实施
- 每次修复在其他地方产生新症状

**停下来质疑基本面：**
- 这个模式从根本上是合理的吗？
- 我们是不是「纯粹因为惯性才坚持下去」？
- 应该重构架构还是继续修复症状？

**在尝试更多修复之前与用户讨论**

这不是假设失败——这是架构错误。

## 危险信号 - 停下来遵循流程

如果你发现自己在想：
- 「先快速修复，以后再调查」
- 「试着改一下 X 看看行不行」
- 「加多个改动，跑测试」
- 「跳过测试，我手动验证」
- 「可能是 X，让我修一下」
- 「我不完全理解但这可能有效」
- 「模式说 X 但我想换一种方式」
- 「主要问题是这些：[没有调查就列出修复]」
- 在追踪数据流之前提出解决方案
- **「再试一次修复」（已经试过 2+ 次时）**
- **每次修复都在不同地方暴露新问题**

**以上所有都意味着：停下来。返回第一阶段。**

**如果 3+ 次修复失败：** 质疑架构（见第四阶段第 5 步）

## 常见合理化借口

| 借口 | 现实 |
|------|------|
| 「问题很简单，不需要流程」 | 简单问题也有根因。流程对简单问题很快。 |
| 「紧急情况，没时间走流程」 | 系统化调试比猜测-检查-再猜**更快**。 |
| 「先试这个，然后再调查」 | 第一个修复定下基调。从一开始就做对。 |
| 「确认修复有效后我再写测试」 | 没有测试的修复不可靠。测试优先能证明它。 |
| 「一次修复多个节省时间」 | 无法隔离什么起作用了。会导致新 bug。 |
| 「参考太长了，我改编一下模式」 | 部分理解保证有 bug。完整阅读它。 |
| 「我看到问题了，让我修一下」 | 看到症状 ≠ 理解根因。 |
| 「再试一次修复」（2+ 次失败后） | 3+ 次失败 = 架构问题。质疑模式，别再修了。 |

## 快速参考

| 阶段 | 关键活动 | 成功标准 |
|------|---------|---------|
| **1. 根因** | 阅读错误、复现、检查变更、收集证据 | 理解**是什么**和**为什么** |
| **2. 模式** | 找到工作示例、对比 | 识别差异 |
| **3. 假设** | 形成理论、最小化测试 | 确认或新假设 |
| **4. 实施** | 创建测试、修复、验证 | Bug 解决，测试通过 |

## 真实影响

来自调试会话的数据：
- 系统化方法：15-30 分钟修复
- 随机修复方法：2-3 小时折腾
- 首次修复成功率：95% vs 40%
- 引入新 bug：几乎为零 vs 常见
